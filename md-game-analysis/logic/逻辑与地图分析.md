# 逻辑与地图分析

基准：SHA-256 `0c97ad517c57cbb8f85e4d0250652e878e0506afb16e5b67440b2e983741279f`。
分析方式：Capstone M68000 反汇编、按实际加载器恢复文件格式、与模拟器 RAM 快照对照。这里的地址均为 ROM 映射地址或明确标注的 RAM 地址。不是全游戏完成度声明。

## 已恢复内容

- 13 个地图索引组，共 117 条目，其中 0000 为空哨兵，116 非空地图条目。条目可重复引用素材，不等于 116 个独立命名地点。
- 三层地图 RLE 解码；当前全部 layer0 为空，layer1 是图形块地图，layer2 是碰撞/事件层。
- 169 条地图尺寸、出生坐标、视口参数记录。地图 ID 与出生记录 ID 是两套独立编号。
- 80 个脚本操作码处理器入口；每组 176 个脚本入口的相对地址表。
- 人物移动格子、事件触发区间、脚本调度方式、实体记录布局的部分字段。
- 一条战斗伤害计算路径、命中判定、1.5 倍伤害判定、随机数公式、15×15 类型倍率矩阵。
- 初始房间地图图形层与模拟器内存逐字节一致验证。

## 游戏运作流程

复位入口 `0x4BA` 初始化 RAM/VDP/声音处理器，然后加载资源、初始角色和开场脚本。每帧在 `0xE40` 等待 VBlank 同步，主循环按 RAM `FFE116` 分流。

零分支调用 `0x97A`（探索方向输入/碰撞/事件），非零分支额外调用大量单位与行动更新。零分支可明确称为探索分支；非零分支与战斗实体/胜败检测相关，尚未在战斗运行画面逐项验证。

系统并非“一次执行完整剧情”：`0xFCA8` 每帧检查脚本激活和继续执行标志。对话、转场、镜头等会清除继续位，等待外部子系统完成后恢复。

## 探索移动与事件

证据地址：`0x97A–0xE3E`、`0x31EA–0x32C2`。

| RAM | 用途 | 证据 |
|---|---|---|
| FFE002/FFE004 | 主角世界 X/Y（16 位） | 0x31EA、0x3218 |
| FFE006 | 方向：0 上、1 下、2 左、3 右；脚本运行中可为 FF | 0x3236 与运行快照 |
| FF6014/FF6016 | 摄像机偏移 X/Y | 0x31EA、0x2C92 |
| FFE104/FFE105 | 摄像机格坐标（带符号） | 0x2C92、0x2CB0 |
| FFE106/FFE107 | 地图逻辑宽/高（格） | 0x2C44、0x3284 |
| FFE108/FFE109 | 图形层宽/高（格） | 0x2C50、0x2FFC |
| FF6030 | 移动/等待计数器；普通单格移动置 32 | 0xAC0、0xCCE |
| FF603C | 前方格事件/碰撞字节 | 0x32B4、0xD30 |
| FFD000 | 地图碰撞/事件层 | 0x32A2 |

```text
cellX = playerX >> 5
cellY = playerY >> 5
frontCell = cell + directionDelta
index = frontCell.y * mapWidth + frontCell.x
value = RAM[0xFFD000 + index]
screenX = playerX - cameraX + 128
screenY = playerY - cameraY + 128
```

一个逻辑格为 32×32 像素。方向键检查优先级：左、右、上、下，使用持续按下状态 FF6003；交互键使用 FF6004 新按下沿。

`0xD30`：格值 1..0x4F 可触发脚本；0 不触发。`0xD92`：格值 0x51..0x7F 进入另一触发路径，0x50 被排除。交互键位 6 的分支仅当格值 0x80..0xAF 时进入 `0xDF4`；否则调用 `0x182AA` 的人物交互搜索。不能把高位格值简单统一解释成“墙”；需要结合脚本、NPC 和地形规则。

## 地图格式与导出

加载函数 `0x2D80` 依次将三个 RLE 流解到 FFB000、FFC000、FFD000。每层解码后输入指针自然接到下一层。

```text
0x00..0xEF: 原样输出一个字节
0xF0: 切换单字节重复模式（每层初始模式）
0xF1: 切换双字节重复模式
0xF2..0xFE: 重复次数 = 低4位，再读取1或2个字节作为重复单元
0xFF n: n非零则重复n次；n=0终止当前层
```

资源统一按 `highByte(mapId)` 取一级指针，再以 `lowByte(mapId)*4` 取二级指针：

| 表 ROM 地址 | 内容 |
|---|---|
| 0293EA | 三层 RLE 数据 |
| 032182 | 4bpp 原始图块流，加载到 VRAM 图块号 0x200，word 3402 终止 |
| 0770A6 | 组合块；正常图形层每块32字节，16个VDP图块word组成4×4 |
| 0DD744 | 地图调色板；0x2D00 装载前32色 |
| 0DE088 | 出生/尺寸记录组；以出生ID低字节×16索引 |
| 0E2DE2 | 脚本组；内部为相对有符号word入口 |

出生记录字段：0/1 逻辑宽高，2/3 图形层宽高，4/5 摄像机格坐标，6..7/8..9 世界X/Y，10方向，11动画，12..14附加状态，15本加载器未读取。最后组在 0xDEB4C 前结束；0x182F8 独立引用 0xDEB4C 作为其他表，支持边界判断。

地图文件在 `maps/`。`map_dimensions_candidates.json` 由脚本数据中 `0012 mapId spawnId` 模式与记录尺寸面积双重筛选得到，仍需注明“候选”，因为尚未对全脚本进行控制流解析；其中有315次匹配，覆盖113个地图ID。

## 运行验证

快照 `runtime/captures/start_1264` 中可见开场室内对话“少爷，出去玩”。模拟器原生RAM按主机小端word保存，交换每对字节后：

- FFE100=0106，FFE102=0100，逻辑/图形层都是10×10。
- `01_06_layer1.bin` 的100字节与 RAM FFC000 开始100字节全部一致。
- 事件层100字节中98字节一致；索引84和85由静态0变为运行66（0x42）。说明事件层会被游戏运行修改，静态地图并非永久碰撞表。
- 主角坐标为 (160,128)，摄像机格坐标 (0,1)。方向字节此时 FF，不能把静态四方向范围套用于所有脚本时刻。
- 脚本指针 FF6130=0x0E300C，当前脚本号 FF6138=0x41。

差异和来源见 `runtime_map_validation.json`。

## 脚本虚拟机

调度器 `0xFCA8–0xFD44`：

```text
if moveCounter != 0 or !scriptActive or !scriptRunnable: return
pc = RAM32[FF6130]
op = readBE16(pc); pc += 2
if op == FFFF: endScript(); restoreControl(); return
if op > 0FFF: continue reading next word
handler = ROM32[FD46 + op*4]
call handler
if FF6157.bit0: clear bit and execute next command immediately
else return to frame loop
```

处理器表实际存在80项（0..79）；调度器检查0xFFF不是80，不能推论支持4096个有效操作码。

已确认操作：0 对话ID（word参数，表0xBC6E4）；3 初始化两组12/18个单位状态；5 从脚本载入64字节实体记录（前置槽索引word）；7 设置最近新建单位的类型字节；0x12 设置地图ID和出生ID（两个word）；0x13 实际加载地图资源；0x15 等待计数器（word）；0xFFFF结束。

其余处理器见 `script_opcodes.json`，未确认语义明确标为 unresolved。`script_entrypoints.json` 包含13组×176入口，其中组0/1共享同一bank，不代表2288个独立剧情。

## 战斗实体与数值

实体基址 FFE780，步长0x40；12个前部槽加18个后部槽，共30个。后18槽基址 FFEA80。`0x1011E` 从脚本复制完整64字节，`0x1009E` 对两组分别设置状态。阵营语义由结构和胜败检查推断，尚需战斗画面确认。

| 字段偏移 | 证据支持的含义 |
|---|---|
| +00 | 类型/有效标识，0作为空槽 |
| +02,+04 | 世界X、Y word |
| +0C..0F | 多种状态效果；+0E影响攻击减半，+0F影响防御减半 |
| +10 | 成长/等级比较字段候选，用于行动后经验计算 |
| +11 | 经验累计字节候选 |
| +12 | 当前生命word：命中后扣伤害、下溢钳为0 |
| +14,+15 | 两类攻击属性byte |
| +16,+17 | 两类防御属性byte |
| +18 | 1.5倍伤害触发阈值byte |
| +19,+1A | 命中/抵抗计算字段byte |
| +21 | 类型/职业索引byte，访问15×15矩阵 |

攻击方索引 FF606B；目标索引 FF609F；技能编号 FF60BC；攻击模式 FF60BB（本函数0取第一类属性，其余取第二类）。技能表0x028E54，每项8字节，编号从1开始。

### 伤害路径：0x6070–0x611C，调用点0x5DE2

```text
A = attacker[mode == 0 ? 0x14 : 0x15]
if attacker[0x0E] != 0: A >>= 1
A += skillTable[skillId-1][0]
M = matrix[attacker[0x21]][target[0x21]]
if M != 0: A = floor(A * M / 10)
D = target[mode == 0 ? 0x16 : 0x17]
if target[0x0F] != 0: D >>= 1
baseDamage = max(1, A - D)
```

矩阵从0x611E开始，共225字节。**矩阵值0表示不改变倍率，不表示0伤害。** CSV `class_multiplier_15x15.csv` 保留原值；正值8/12/15/20等对应0.8/1.2/1.5/2.0。职业/类型名称尚未对应。

紧接调用 `0x5F9C`：生成随机值R，若R≤攻击方+18，则 `damage += floor(damage/2)` 且 FF6103=2。结合伤害效果可以称“暴击候选”，中文UI名称未验证。随后0x5E12从目标+12扣除伤害，下溢时归零。

### 命中/状态成功：0x5FDC

```text
threshold = (attacker[0x19] + skill[6]) mod 256
if target[0x0C] != 0: success = true
else if threshold < target[0x1A]: success = false
else success = (nextRandomPercent() <= threshold - target[0x1A])
```

这一路径同时被普通伤害和部分状态技能调用。注意比较是≤，而且先以8位加法计算，不能直接改为常见的百分比浮点掷骰。

### 随机数：0x604E

```text
state = (state * 32719 + 3) mod 32749
R = floor((state & 63) * 100 / 64)
```

state在FF6100，是16位。初始种子来自VDP计数寄存器（0x73A），因此时序影响后续随机结果。R只有64种离散取值，0..98，并非均匀100个整数。复刻若要重现录像，需要相同种子与相同调用顺序。

## 追加：成长、经验、技能/道具表（已恢复）

### 确定性成长

`0x14C80` 按实体+21取 `0x14DAA` 的15项指针表；每职业32字节，8属性×4字节，每组为 `base,numerator,denominator,cap`。`0x14FC6` 实现：

```text
value = min(cap, base + floor((level - 1) * numerator / denominator))
```

8项依次写入最大生命+1E（word）、攻击0 +14、攻击1 +15、防御0 +16、防御1 +17、暴击阈值+18、命中+19、抵抗+1A（其余byte）。实体+10已确认是等级，+11是经验，+12是当前生命，+1E是最大生命。不是每次升级随机加点。

实体+2A为被动装备/加成ID：0x70、71、72、73、74、75、76分别让攻击0、防御0、攻击1、防御1、命中、抵抗、最大生命在基础封顶计算**之后**乘11再除10。因此装备加成可能超过基础cap，不能提前把最终值夹回cap。暴击阈值未走该装备加成。

`class_growth.json` 导出15职业原始参数；`class_growth_levels_1_99.csv` 导出1485行（不含装备加成）。初始快照7个有效战斗实体的8项属性、共56个数值，全都与此公式精确相同，见 `runtime_growth_validation.json`。

实体+24是职业/形态子类型（1起）；`0x14D72` 以 `subtype-1` 查询0x14D8C的30个字节并写+1B。这个字段可能是移动范围，仍需地图移动代码交叉验证。

### 经验与进阶

`0x5E4E` 在伤害结算后：`index = targetLevel + 5 - attackerLevel`。若8位减法借位，经验+1；否则index上限13。普通命中用0x5F08表 `[2,5,10,15,20,25,33,50,70,80,100,100,100,100]`；扣生命发生下溢时切换0x5F16表 `[5,12,18,24,30,42,57,80,100,100,100,100,100,100]`。**生命恰好扣到0不发生借位，不能把代码条件粗略改成“HP==0就用击杀经验表”。**

经验按byte累加，大于99时减100、等级加1、设置FF614F待处理。随后0x14C12负责按成长表重算属性并启动升级提示脚本。

状态技能的 `0x14FF2` 使用不同经验索引：`targetLevel-attackerLevel`，借位则+1，否则上限8，再查0x5F08。不是所有行动同一经验规则。

`0x5F24` 有15职业进阶链，每条 `(子类型,阈值等级)` 成对排列。等级等于阈值时改为下一对子类型；阈值100是结束标记。例职业0：子类型1在13级变2，25级变3；具体职业中文名待名称图谱对应。详见 `class_progression.json`。

## 追加：音效命令路由

`0x1E41D4` 当FF6D00最高位为1时，以低15位查 `0x1D84B6` 的4字节条目，共177条，到0x1D877A结束。

- 若条目首word为负，写entry[2]到Z80 A00022、entry[1]到A00020。
- 否则走68000管理的PSG声道，entry[0]高半字节决定声道状态槽，低半字节为优先级；entry[1]&0x7F索引0x1D877A声音序列指针表。
- PSG指针表122项，许多指向同一静音/空序列，因此177个命令不是177种独立声音。
- PSG序列0x80结束；0x81读一字节音量；0x82跳过一字节再读BE16声音命令，并转调命令路由；0x7F单步静音；其他低于0x80的字节与下一字节组成音调写入，每次帧更新前进一条音调/静音记录。

逐条路由在 `sound_command_routes.json`。有些索引可能只用于停止或控制，不应把导出静音视为解析失败或“无素材”。

|---|---|
| +1,+3,+5,+7 | 固定签名06 09 01 08 |
| +9,+B,+D,+F | payload逐字节求和，32位小端 |
| +11,+13,+15… | RAM FFE000开始的连续字节，每隔2个CPU地址写1字节 |

基址200000保存4088字节（FFE000..FFEFF7）；其他两槽各2040字节（FFE000..FFE7F7）。因此普通槽不会直接保存FFE780之后所有战斗实体，较大槽才覆盖完整战斗实体区。

读档函数0x26FF2检查签名后清理运行内存、恢复相应payload，再重建图形/地图/声音等临时状态；本路径未见校验和比对。另一路0x24CFE明确对4088字节payload求和并校验4个校验字节；不能把这个验证推及每个读档路径。

实际模拟器验证：冻结主循环并屏蔽中断，把A6设为各基址，调用原ROM 0x26C10，三次均完成返回。写出的签名正确，payload与调用前RAM逐字节相同，存储校验和与独立求和一致（较大槽95812、普通槽14898）。全部结果在 `save_probe_results.json`，原始SRAM结构及解出的payload在 `save_probes/`。试验仅写入该模拟器进程的独立内存，没有修改用户原ROM或真实游玩存档。

## 追加：战斗地图加载与最后两张地图尺寸

脚本操作0x25（处理器0x10A32）走不同于探索的加载路径，参数为 `BE16 mapId, byte width, byte height, byte cameraX, byte cameraY`，直接写FFE100/106/107/108/109/104/105，随后调用0x24F06构建战斗状态。它不使用出生记录表。

此前无法确定尺寸的两图因此获得直接参数证据：

- 脚本0xE5E94：`0025 0408 18 0F 04 08`，地图0408是24×15。
- 脚本0xE8F44、0xE9C9A：`0025 0A06 18 19 00 12`，地图0A06是24×25。

尺寸面积分别360/600，与解码层长度一致。相关引用导出为 `maps/battle_map_dimensions.json`，已交给图像流程渲染。全部116个非空地图现在均有可用尺寸依据；其中脚本模式匹配结果尚不能代替每张图实际运行到访。

## 追加：实体初始表与剧情增援记录

`0x151E` 明确从ROM 0x1536复制30×64字节到FFE780。完整30条已解为 `initial_30_units.json`，包括空槽、角色类型、坐标、等级、生命、属性、职业、技能、装备、次数及原始64字节。

脚本操作0x05（0x1011E）和0x43（0x11E2A）携带一个起始搜索槽word与64字节实体记录。对脚本数据区执行操作码、槽范围、坐标32对齐、等级/职业/子职业范围共同筛选，得到198条候选增援/单位模板，导出 `script_unit_candidates.json`。它们是记录实例，可能重复同一个人物，不等于198个独立角色；未解析到达控制流的记录仍标为候选。

常驻人物记录在FFE630，步长16字节；FFE610是以0结束的队伍ID列表。`0x24F06` 将常驻数据扩展为64字节战斗实体，再计算成长并补满生命。常驻字段+0→实体+0、+1→+7、+2..5→+8..B、+6→等级、+7→经验、+8→子职业、+9→被动装备、+A..D→4装备槽、+E→职业。战斗结束的脚本0x27（0x10ACE）把技能/等级/经验/子职业等写回常驻区。它解释了为何普通存档只保存较小范围仍能保留队伍成长。
